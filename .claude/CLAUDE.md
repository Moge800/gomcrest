# CLAUDE.md — gomcrest

このファイルはリポジトリ全体で作業するエージェント向けの指針です。ユーザーの今回の依頼を優先し、実装・検証・PRの状態を日本語で簡潔に報告してください。

## 1. 作業の進め方

- 変更前に作業ブランチ、差分、関連コード・ドキュメント（README、`.docs/`）を確認する。未コミットの変更を上書きしない。
- 複数工程の作業では、目的・作業順・確認方法を短く示してから進める。既存の情報で決められる実装上の選択は自律的に進め、公開APIの形や仕様を左右する不明点だけ確認する。
- 依頼を満たす最小限の変更にする。無関係な整形、リファクタリング、依存追加を混ぜない。
- 不具合は原因と再現条件を確認し、再現するテストを先に書いてから直す。
- 中断やツール失敗後は完了した処理を確認し、必要な部分だけ再開する。完了済み作業を最初から繰り返さない。
- サブエージェントや外部モデルへの委任は、ユーザーの依頼または適用される上位指示に従う。特定のモデルや連携サービスの存在を前提にしない。

## 2. プロジェクトと実行環境

- [gomc-rest](https://github.com/Moge800/gomc-rest)（三菱PLC向けMCプロトコルRESTゲートウェイ）のGoクライアントライブラリ。PLCとは直接通信しない。gomc-rest本体は変更・同梱しない。
- モジュール `github.com/moge800/gomcrest`、パッケージ `gomcrest`。**標準ライブラリのみ**で、外部依存を追加しない。
- Goの下限は `go.mod` の `go 1.23`（gomc-rest-guiに合わせた値）。`go`行を無断で上げない。手元のツールチェーンは新しいことがあるので、1.24以降で追加された標準ライブラリAPIを使わない。
- 対象サーバはgomc-rest v1.4.0以降（`MinimumServerVersion`）。K記法のみv1.7.0以降。サーバの挙動は推測せず、gomc-restの`openapi.yaml`とハンドラ実装（`handler.go`）で確認する。
- 想定利用者はgomc-rest-gui（Wails）、エッジ収集、その他のGoツール。GUIへの組み込みを壊す変更は慎重に扱う。
- 開発機はWindows。E:ドライブは所有者情報を記録しないため、リポジトリがgitの`safe.directory`に未登録だと`dubious ownership`で止まる。グローバル設定は変えず、`git -c safe.directory=E:/Develop/gomcrest ...`等のコマンド単位で回避するか、ユーザーに登録を依頼する。

- 新しいエンドポイントは用途ごとのファイルに置き、`do` / `get` / `post` / `read` / `write`を使う。HTTP処理を重複させない。
- 利用者向けの変更はgodocと`README.md` / `README_jp.md`の両方に反映する。
- `.docs/`は非公開。README等の公開ファイルから参照しない。判断のたびに`.docs/decisions.md`へ新しい順で追記し、方針が変わったら`.docs/plan.md`を、ツールのバージョンが変わったら`.docs/versions.md`を更新する。ただし共有すべき仕様や判断理由を`.docs/`だけに残さず、godoc・README・コミットメッセージ・PR本文にも書く。

## 4. 公開APIと互換性

- 公開API（型、メソッドのシグネチャ、番兵エラー、定数）の変更・削除はgomc-rest-guiに影響する。v1.0.0前でもPR本文で明示し、フィールド追加など後方互換の変更を優先する。
- 全メソッドの第1引数は`ctx context.Context`。タイムアウトとキャンセルは呼び出し側に任せる。
- `*Client`は生成後に変更しない状態を保ち、並行利用を可能にしておく。可変状態を足さない。
- `http.DefaultClient`を使わない。`WithHTTPClient`で渡されたクライアントは書き換えず、浅いコピーに`CheckRedirect`を設定する。
- 自動リトライ、独自のレート制限・並行数制御、ポーリング・購読・変化検知のヘルパー、OpenAPIからのコード生成は追加しない。

## 5. サーバとの通信で守るべき動作

- バリデーションはサーバに任せる。アドレス解析・レンジチェックをクライアントで二重管理しない。送信前に弾くのは明らかに不正なもの（汎用WriteのValues、random系の全空）だけで、`ErrBadRequest`で包み、何も送らない。
- クエリのboolは`"true"` / `"false"`。`/read`は`addr, count, dword, sint`、`/write`は`addr, dword, sint`を常に送る。サーバは未知のパラメータを400にするため、未定義のパラメータを送らない。
- リダイレクトは追わない（3xxは`*APIError`）。トークンをbaseURLのorigin外へ送らないこと、POSTがGETに変わらないことの前提なので崩さない。
- 呼び出し側のctxのキャンセル・期限切れは`ctx.Err()`で判定してそのまま返し、`ErrTransport`で包まない。`http.Client.Timeout`切れは`ErrTransport`とする。
- サーバのエラーは`code`で番兵に対応させ、401はボディがなくても`ErrUnauthorized`にする。gomc-rest以外の応答（プロキシのHTML等）は`Code`を空にし、推測で番兵に寄せない。
- レスポンスは`io.LimitReader`（1 MiB）越しに読む。型や件数が合わないレスポンス、`null`、サーバが必ず返す項目（`plc_status`、`version`）が無いレスポンスは`ErrBadResponse`にし、途中までの値やゼロ値で成功扱いにしない。
- 書き込み・リモート操作は`post`経由で送り、`{"ok":true}`を確認する。2xxでも確認できなければ`ErrBadResponse`にする。
- `ErrBusy`はPLCで未実行（書き込みも再送可）、`ErrRequestTimeout` / `ErrTransport` / 書き込みでの`ErrBadResponse`の後は実行されたか不明で、再送は二重書き込みの恐れがある。この区別をgodoc・READMEから消さない。
- 新しいサーバ機能に対応するときは、必要なgomc-restのバージョンをdocコメントとREADMEに書く。

## 6. 秘密情報と実機の保全

- トークンをコード・テスト・ログ・コマンド出力・PR本文・コメントへ載せない。例やテストにはダミー値（`s3cret`等）を使う。
- 結合テストは実機のPLCを操作する。書き込みテストは`GOMCR_TEST_ALLOW_WRITE=1`のときだけ実行し、使うデバイス（`GOMCR_TEST_WORD_ADDR`から2ワード、`GOMCR_TEST_BIT_ADDR`から16ビット）を終了時に元の値へ戻す。この保全を崩さない。
- リモート操作（RUN / PAUSE / STOP / LATCH CLEAR / RESET）はPLCを止めるため、結合テストに含めない。ユーザーの明示的な指示なしに実機へ実行しない。
- 結合テストを実行していないのに、実機で動作確認済みと報告しない。模擬サーバ（httptest）での結果を実機での成功として扱わない。

## 7. 変更に応じた検証

以下はプロジェクトルートからGit Bashで実行する。関連する確認を選び、実施内容・結果・未確認事項をPRへ記載する。

```bash
gofmt -l .                          # 出力が空であること
go vet ./...
go vet -tags integration ./...      # 結合テストのコンパイル確認
go test ./...
go test -race ./...                 # cgo（gcc等のCコンパイラ）が使える環境のみ
GOTOOLCHAIN=go1.23.0 go test ./...  # Go 1.23で使えない標準ライブラリAPIの検出

# 結合テスト（実機またはGX Simulatorにつないだgomc-restが必要）
GOMCR_TEST_URL=http://192.168.0.10:8080 go test -tags integration ./...
```

- `-race`はcgoが必要。使える環境では実行し、使えない環境（Cコンパイラのない現在のWindows開発機など）では省略して、CI（ubuntu、Go 1.23 / stable）の結果をPRで確認する。省略した場合はその旨を報告する。
- コードの変更にはhttptestのテストを伴わせ、送信内容（メソッド・パス・クエリの完全一致・ボディ）とエラーの対応を確かめる。新しい分岐は、壊すとテストが落ちることを確認する。
- 文書のみの変更は、記載したパス・コマンド・API名と現状の一致、英日READMEの対応、および`git diff --check`を確認する。全テストや実機接続は不要。
- 実機が必要な確認（結合テスト）は、未実施なら明記する。

## 8. Git・PR・レビューの運用

- 通常は`main`から`feat/<内容>`（`fix/`、`docs/`、`test/`、`chore/`）ブランチを作り、変更をコミット・プッシュして、`main`宛てのPRを作成する。作業前にリモートとの差分と既存の作業を確認する。
- コミットメッセージとPR本文は英語（gomc-restに合わせる）。コミットは`feat:` / `fix:` / `docs:` / `test:` / `refactor:` / `chore:`の形式にする。
- `main`への直接プッシュは、その変更についてユーザーが明示的に指示した場合だけ。強制プッシュで共有履歴を変更しない。
- PR本文には、**背景・解決したい問題、変更が必要な理由、改善内容、採用方法の理由、影響範囲と互換性（公開APIの変更有無）、検証結果、未確認事項・残る課題**を具体的に記載する。
- CodexのGitHub連携がこのリポジトリで有効な場合は、PRを作成したら会話欄へ **`@codex review`** とコメントしてレビューを依頼する。PR本文への記載だけで済ませない。
- `@codex review`を連投しない。前回のレビューへの返答・完了を確認してから、指摘への修正と検証をまとめて行い、必要な再レビューを1回依頼する。実行中に追加修正しても、前回の返答が来るまでは再投稿しない。
- 指摘があれば根拠を確認し、修正・検証・追加プッシュを行う。指摘への対応と検証結果を返信する。採用しない場合も理由を説明し、未対応事項を隠さない。
- 修正後は再度`@codex review`を依頼し、**最新の変更へのレビューが完了し、新たな対応事項がなくなるまで繰り返す**。指摘スレッドとCIの結果も確認する。返答がないことやリアクションだけで「指摘なし」と判断しない。
- 通知が利用できる場合は通知を待つ。通知が利用できない場合だけ間隔を空けて状態を確認し、短間隔の連続照会を避ける。利用制限・連携失敗等でレビューできない場合は、原因と未完了の状態を報告する。
- PR作成後はURLと変更・検証・レビュー状況を報告する。**マージ、リリース、タグ作成は管理者が行う**。レビュー完了をマージ許可として扱わない。バージョンは提案だけ行う（v1.0.0前は機能追加でminor `0.x.0`、修正・文書でpatch `0.x.y`）。
- マージ後に`main`へ戻すときは、未保存の作業を確認してから同期する。別の作業ブランチや手元の`.docs/`を削除しない。
